## Architecture / logic changes

The PS3 log producer now formats and copies fixed-size records into a 128-entry SPSC queue. A lowest-priority PPU thread owns writes and batch flushes. Queue depth/overruns and maximum write/flush times are exposed. Shutdown requests a bounded 500 ms drain; if the writer remains blocked, cleanup avoids closing its stream concurrently. Host logger tests continue to exercise synchronous mode.

RTSP parse, session-handler, response-send, and prior total handler timing are now separately visible at microsecond resolution. RTP resynchronization is conditional: queue full and sequence lead greater than 128 packets. It counts stale frames, drains bounded pending socket data, clears resend expectations, signals the app, clears PCM/resampler history, and re-enters the existing prebuffer gate. Capacity is not increased.

The supplied JPEG was decoded to RGB and saved losslessly as a PNG without source metadata. The 320x176 icon and 1920x1080 PIC1 are verified direct resizes. The same source now feeds the in-app background. Only the XMB title (`AIR PS3`) and RAOP service-name suffix (`AirPS3`) change; `AIRPLAY02` and its content identity stay intact.

## Runtime behavior changes

While the PS3 logger worker is active, log events no longer call filesystem write/flush on the RTSP/audio producer path. Under sustained writer stalls, the 128-entry queue can overrun and drop diagnostic records; this is counted. On a full RTP backlog more than 128 packets behind live audio, the app discards stale queued audio and briefly re-prebuffers instead of traversing obsolete sequence positions.

No change was made to VSH compositing or system-menu drawing. The app cannot enforce transparency in the GameOS menu; the existing callback/refresh path remains.

## Known limitations / follow-ups

- Async writer tests currently cover host synchronous logging; worker concurrency and starvation require cross-build and hardware validation.
- A failed sink cannot write a diagnostic about its own failure. After a >500 ms shutdown stall, the app skips `fclose` to avoid racing the writer, and buffered tail loss is possible.
- The supplied mission's exact 5.435-second event was not independently reproduced from a locally identified raw trace.
- No PS3 test confirms the image/icon, RAOP name, automatic recovery sound, XMB visual resume, or logger scheduling.

## Risks introduced

The PPU writer adds one low-priority thread and a fixed 20 KiB record queue. A queue overflow drops logs; a writer failure can prevent final shutdown records from reaching disk. Automatic recovery intentionally drops stale audio and can cause a short interruption; a mistaken threshold classification could discard recoverable packets. Hardware testing must verify the real queue thresholds and XMB behavior before wider use.

## Decision record

### Decision 1 — Move filesystem work off the producer path

- **Context:** Per-event `fflush` may block the shared receiver/audio loop; the cause is not proven.
- **Options considered:** Remove all logs; only buffer through stdio; introduce asynchronous writer; split RTSP and audio into new worker architectures.
- **Chosen:** Fixed SPSC log queue plus a lowest-priority writer, with overrun counters and bounded shutdown drain.
- **Tradeoffs:** Adds one thread and bounded memory; a stalled writer can lose final tail events. Avoids blocking the receiver producer on filesystem calls when the worker starts successfully.

### Decision 2 — Recover only at demonstrable queue saturation

- **Context:** Existing capacity is 256 and normal occupancy is far lower; blindly increasing it would add latency and memory.
- **Options considered:** Increase capacity; discard newest; always advance the head; clear the queue on every gap; conditionally restart when full and >128 packets behind.
- **Chosen:** Conditional live-edge resync at full queue and >128 packet lead, with cumulative drops/resync counts and resend/PCM reset.
- **Tradeoffs:** A severe burst may produce a brief audible discontinuity; threshold should avoid ordinary jitter and remain measurable.

### Decision 3 — Use the attached artwork through lossless source pixels

- **Context:** Supplied JPEG has embedded source metadata, but the user asked for the exact artwork.
- **Options considered:** Commit original JPEG bytes; regenerate a generic asset; store decoded RGB pixels without metadata and derive PNG assets.
- **Chosen:** Metadata-free PNG of the original decoded RGB pixels, with deterministic derivatives.
- **Tradeoffs:** PNG bytes differ from the JPEG, but its decoded source pixels are identical. The in-app image is resized to screen dimensions.

### Decision 4 — Preserve VSH as the compositor owner

- **Context:** The screen resumes dim/frozen after the PS menu; app framebuffer is not the system menu layer.
- **Options considered:** Modify app content while menu is open; draw over the menu; preserve existing callback rendering until physical evidence isolates the fault.
- **Chosen:** Preserve existing bounded refresh behavior and do not draw over or claim control of VSH.
- **Tradeoffs:** The visual resume defect remains pending hardware investigation.
