# v0.1.36 bounded late resend recovery

## Timestamp in EDT

2026-11-07 15:53 EDT

## Scope of the pass

Analyzed a fresh read-only v0.1.35 hardware capture and implemented bounded recovery for valid retransmission packets that arrive after their tracking slot is absent but before playout. Added aggregate rejection counters and an integration test. Updated engineering memory and stability status.

## Why this pass was needed

The v0.1.35 log showed active PCM underflow coinciding with RTP sequence gaps, resend requests, and no recovered packets. Existing reject telemetry could not distinguish an expired/unmatched tracking record from a packet that was already too late or duplicated.

## Architecture / logic changes

The RTP receiver still validates packet type and negotiated peer port. If an otherwise valid resend has no outstanding range, it may enter the bounded queue only if its sequence is behind the highest original RTP sequence by 1–256 packets. Existing queue rules reject sequences already played, duplicates, malformed packets, and queue overflow. New counters distinguish untracked recovery from unmatched, late, duplicate, full-queue, and invalid rejection. Counters are logged in five-second aggregates to avoid per-packet log pressure.

## Runtime behavior changes

A still-playable retransmission is no longer discarded solely because its outstanding request bookkeeping entry expired or was cleared. Already-played audio is not replayed. The audio resampler, PCM format, display path, controller path, and firmware configuration are unchanged.

## Immediate results

The capture contains 2,048 received RTP packets, 302 sequence gaps, 209 late packets, 58 resend requests, zero recovered packets in periodic totals, zero ALAC failures, and 102,200 active-stream PCM underflow frames. Three retained buffer snapshots were 5,654, 4,533, and 1,037 frames. The capped log wrapped, so startup identity and a complete session timeline are unavailable. The source regression for a still-playable untracked resend passes.

## Known limitations / follow-ups

Standalone v0.1.36 ELF/PKG build, RPCS3 install/launch/audio continuity, physical hardware behavior, new categorized resend counters, audio quality, and XMB resume remain unverified. The installed EBOOT hash was captured but not compared with an extracted local v0.1.35 payload. A hardware run is required to learn whether the newly accepted resend path reduces underflows.

## Risks introduced

Only valid audio retransmissions from the negotiated control port are considered. Sequence admission is limited to a 256-packet window, and the queue rejects already-played, duplicate, malformed, or capacity-exceeding packets. A sender that supplies unusual sequence ordering may still be rejected; counters now expose the reason. No console firmware, installed files, boot configuration, or experimental SPRX were changed.

## Decision record

### Decision: Accept bounded untracked retransmissions

- **Context:** The live log showed no resend recoveries, while valid-format rejection records and active PCM starvation coincided with RTP gaps.
- **Options considered:** Keep rejecting unmatched responses; accept any response from the peer; accept only responses inside a bounded still-playable sequence window.
- **Why this option was chosen:** It repairs a confirmed overstrict rejection path while retaining peer-port, sequence-window, queue-capacity, duplicate, and playout protections.
- **Tradeoffs accepted:** Some recovered packets may remain unusable if they arrive after playout. The new counters and hardware test will show whether tracking expiry was materially responsible.

### Decision: Leave the resampler and RSX path unchanged

- **Context:** Sample-rate conversion already uses an integer phase accumulator for 44,100 to 48,000 Hz, while the hardware log directly reports active PCM starvation. Display resume remains outside this capture's reliable evidence.
- **Options considered:** Replace the resampler, change PCM capacity, modify RSX presentation, or first repair and measure retransmission recovery.
- **Why this option was chosen:** A broader DSP or graphics change would not be supported by the measured boundary and would raise regression risk.
- **Tradeoffs accepted:** Crackling, dropouts, and flicker are not claimed fixed in this pass.
