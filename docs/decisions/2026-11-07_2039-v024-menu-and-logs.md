# Restore PS-menu scanout and preserve launch logs

**Timestamp:** 2026-11-07 20:39 EDT

## Scope of the pass

Prepare v0.2.4 / SFO 00.44 with two focused changes: resume paced display flips while the PS system menu is open, and append per-launch diagnostic sessions instead of truncating/wrapping prior history.

## Why this pass was needed

The v0.2.3 hardware log records DRAW_BEGIN and MENU_OPEN but no close. User reports the menu was invisible and START stopped working after pressing PS. Separately, the current log opener truncates and the 16 KiB global wrap erases earlier sessions.

## Architecture / logic changes

While menu-open, the static renderer alternates unchanged buffers at a 16.667 ms minimum interval so VSH can refresh its overlay. Normal idle rendering remains static to limit flicker. The diagnostic logger opens with append mode; its 16 KiB budget resets per app launch, not per file. Each APP_START event carries UTC time. When a run nears its cap, it appends LOG_SESSION_CAPPED and ignores later events until the next launch.

## Runtime behavior changes

Expected: PS-menu drawing can receive new scanout frames; previous log sessions remain intact across relaunches. These expectations are not yet hardware-verified.

## Validation performed

- Reviewed the v0.2.3 private log: 3,673 bytes, SHA-256 `ae8689248b6e0bdac6d8a25aa1dd06e7a1f75acc1151470b730156726dcd280e`.
- Confirmed event sequence: APP_START; four seconds later DRAW_BEGIN and MENU_OPEN; 18 pad samples in the next heartbeat, then zero; no raw digital transition, MENU_CLOSE or APP_STOP.
- Added a host regression to cover two APP_START timestamps, retained first-session events, a per-session cap marker, and rejection of post-cap writes.
- Full Lima ASan/UBSan host suite and PPU component compilation passed, including the append-only regression; standalone ELF/package validation and hardware test remain pending.

## Immediate results

The append-only regression passes: both launch timestamps and first-session events survive reopening; the second session stops at its 16 KiB cap marker. The PS-menu refresh change compiles in the PPU component build. The exact committed source was subsequently built, packaged as v0.2.4 / SFO 00.44, and installed; deployment evidence is in `docs/decisions/2026-11-07_2150_v024_build_install.md`.

## Known limitations / follow-ups

Menu visibility remains a hypothesis until tested on PS3. Append-only total log size grows by up to 16 KiB per app launch; the cap bounds each run but does not rotate or delete history. Verify free HDD space over time.

## Risks introduced

Menu-time refresh may reintroduce display flicker while the system menu is active; it does not cause continuous flips during ordinary static display. Append-only diagnostics consume cumulative disk space across many runs. No firmware or boot-plugin changes are involved.

## Decision record

### Refresh only during system-menu drawing

- **Decision:** Force paced buffer flips while `system_menu_open`, without changing ordinary static-screen behavior.
- **Context:** The app stopped flipping when no redraw was pending, while VSH logged menu drawing but the user saw no menu.
- **Options considered:** Keep the static renderer; flip continuously at all times; flip only during the menu-open interval.
- **Why this option was chosen:** It targets the observed boundary while limiting flicker outside menu use.
- **Tradeoffs accepted:** It may not fix overlay rendering and needs a hardware test.

### Append immutable sessions with a per-run cap

- **Decision:** Append to the existing log and apply the 16 KiB ceiling per app launch.
- **Context:** `wb` and LOG_WRAPPED erased earlier diagnostic history.
- **Options considered:** Keep global wrap; rotate/delete old files; append capped sessions.
- **Why this option was chosen:** It preserves launch-to-launch evidence with no cleanup automation or file deletion.
- **Tradeoffs accepted:** Total file size grows proportionally to number of launches.
